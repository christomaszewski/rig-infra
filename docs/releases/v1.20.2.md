The `fleet-ros` base image no longer changes when only its replay check script changes, and the
messages overlay builds without contacting Docker Hub for a Dockerfile frontend.

- `base/Dockerfile` copied `check_replay_runtime.py` into the image ahead of the `io.rig.*`
  labels. The script arrived in v1.18.0 and was edited in v1.19.0 and v1.20.0; each time the base
  got new layers and a new digest, and the messages overlay and every service image built
  `FROM` it rebuilt in full.
- The check now runs in a `replay-gate` stage of its own, with the script bind-mounted. The
  image copies one constant marker file from that stage,
  `/usr/local/share/rig/replay-runtime-checked`, and then sets its labels. BuildKit keys the
  copy on the marker's content, so an edited script runs the check again, writes the same
  marker, and every layer of the image is reused. Each architecture keeps its manifest digest,
  which is what Rig v0.2.82 compares before it keeps the published index digest and leaves
  dependents cached.
- The labels still depend on the check. It runs against the package layer the image ships, a
  failing check fails the build, and both build targets start from the labelled stage.
- `msgs/Dockerfile` no longer names `docker/dockerfile:1` as its frontend. With the directive,
  every overlay build resolved that image on Docker Hub before its first step, a fully cached
  build included, so a rate limit or a disconnected builder failed the overlay and with it
  `rig build --offline`. The file uses only what the frontend built into BuildKit 0.10 and later
  provides.
- Three guards keep both properties. `tests/test_dockerfiles.py` fails if any Dockerfile names a
  frontend. `base/test_replay_contract.py` asserts the gate's structure: the script is only
  bind-mounted, the marker is a literal written after the check, and the labels follow the
  marker. The replay-runtime workflow rebuilds the base with an edited script and requires the
  same layers and creation time.

### Upgrade and limits

Launchers, configurations and the player provider are unchanged, and Rig v0.2.81 still works.
Keeping a published index digest needs Rig **v0.2.82**; with an earlier Rig every build
publishes a new index and dependents rebuild as before.

The first build after upgrading publishes a new `fleet-ros` digest, because its layers changed,
so the messages overlay and the service images rebuild once. The overlay may also get new layers
of its own on a builder whose built-in frontend differs from `docker/dockerfile:1`.

Images no longer contain `/usr/local/lib/rig/check_replay_runtime.py`. To run the check against
an image, mount the script:

```sh
docker run --rm -v "$PWD/base/check_replay_runtime.py:/check_replay_runtime.py:ro" \
    <registry>/fleet-ros:<tag> python3 /check_replay_runtime.py
```

A builder with no cache for the base's steps still produces a new digest: a new builder,
`--no-cache`, or cache the builder has collected. The base also changes when its package or
label steps change or when the parent `ros` image is pulled again. Editing the marker's text
changes the image.

All four services in this collection share v1.20.2: `zenoh-router`, `ros2-bag-logger`,
`ros2-bag-player`, and `ros1-bag-logger`.

### Validation

Measured with Docker Engine 29.9.3, Buildx 0.38.1, a BuildKit 0.34.2 `docker-container` builder
and a local registry, publishing through `base/build.sh` and `msgs/build-msgs.sh` as Rig does
(`--push --provenance=mode=min`); arm64 native, amd64 emulated.

- v1.20.1 base: a comment-only edit of the script published a different arm64 manifest.
- This release: a comment-only edit and an edit that adds a check each ran the gate again and
  published the same manifest. An arm64 and amd64 build kept both manifests. A check made to
  fail failed the build and left the tag on the last good publication. A `--no-cache` build
  published a new manifest, which the next ordinary build and a build after a further script
  edit both kept. BuildKit 0.10.6 also kept the manifest across a script edit.
- Overlay: each build with the old Dockerfile resolved `docker/dockerfile:1`, cached or not, and
  on a builder with no route to Docker Hub it failed there with every step cached. The new
  Dockerfile resolved nothing and built on that builder. An apt-only overlay kept its manifest
  across the change. The apt-only overlay and a source overlay from a local checkout (named
  context, ssh and bind mounts) built on BuildKit 0.10.6.
- All 26 local pure-test scripts passed (265 tests), and `rig certify --require-build-check`
  passed for all four services with Rig v0.2.82. The steps of the replay-runtime and
  runtime-images workflows passed locally on arm64 against the new images, including all 21
  native ROS acceptance tests without skips on both the base and the overlay.

Not run: `rig build` end to end with Rig v0.2.82, the GitHub workflows themselves, and the
amd64 acceptance tests, which run in CI. Rebuild times of dependent images were not measured
again.
